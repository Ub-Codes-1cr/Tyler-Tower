## 4. ERROR HANDLING, RUNTIME RULES & SAFETY PROTOCOLS
To preserve operational reliability and prevent token exhaustion or execution deadlocks, Tyler Tower enforces the following runtime constraints:

### 4.1 Execution Rules & Memory Boundaries
- Idempotent Execution: Rerunning a batch pipeline on events_manifest.json must never overwrite previously generated scripts flagged as APPROVED or RENDERED unless the --force-refresh flag is explicitly appended.
- Context Window Protection: Agents operating within Tyler Tower must read only the specific event record and referenced markdown persona required for the active task. Full-directory dumps into system prompt contexts are strictly prohibited to prevent hallucination and unnecessary API spend.
- Deterministic Output Location: All generated scripts must be written exclusively to brain/reels_output/reel_[ID].md. Intermediate drafts must be cleared from working memory upon completion.

### 4.2 Hallucination & Consistency Guards
- No Fictional Events: Tyler Tower is barred from generating promotional reels for events that do not possess a corresponding, verified record inside events_manifest.json.
- Bangalore Geo-Fencing: All location context must reflect accurate Bangalore geography (e.g., an event recorded at Indiranagar cannot be script-located to Bellandur).
- Metric Verification: Challenge counts, follower numbers, and financial goals quoted in scripts must match the approved ground truth: 100 Tech Events in 50 Days, 1K1 in 365 Days, 100k Community Members, and ₹25L / ₹1 Crore Milestones.
